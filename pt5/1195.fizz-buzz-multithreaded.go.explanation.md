# 1195. Fizz Buzz Multithreaded - Go

## Go implementation notes
The number goroutine orchestrates the sequence with unbuffered channels and waits for acknowledgements from word-printing goroutines.

## Go interview framing
In Go, explain both the algorithmic invariant and the concrete representation: slices for dense arrays/queues/stacks, maps for sparse lookup, structs for queue states or records, and channels or `sync` primitives for concurrency. Then walk through how the code mutates that representation while preserving the invariant.

## Core idea
A shared counter determines the next token. All four worker methods wait on one condition variable until their predicate matches the counter.

## Algorithm
1. Store `current`, initially `1`.
2. Each method calls a helper with its predicate and print action.
3. Under the condition lock, wait while the counter is in range but the predicate is false.
4. When true, print, increment, and notify all waiting threads.
5. When the counter exceeds `n`, notify and return so all threads terminate.

## Data structure choice
A condition variable is better than busy waiting because threads sleep until the shared state changes.

## Correctness argument
The lock ensures only one thread observes and advances a given `current` value. The predicates partition numbers from `1..n`, so exactly one method prints each token, in increasing order.

## Complexity
There are `n` print steps. Time is `O(n)` plus synchronization overhead; space is `O(1)`.

## Interview explanation
Start by naming the invariant: what state is being stored and why that state is sufficient. Then explain the transition or traversal in the same order the code executes. Finally, connect the stopping condition to the returned value. This keeps the explanation grounded in the code instead of sounding like a memorized trick.

## Tests and edge cases
- `n=15` prints the full FizzBuzz sequence.
- Small `n`, such as `1`, wakes non-number threads to terminate.
- Starting threads in any order still follows the counter.

## Possible improvements
The current solution is chosen for clarity and interview reliability. If constraints were much larger, the main improvement would be to reduce the stated bottleneck in the complexity section, while keeping the same correctness invariant.
