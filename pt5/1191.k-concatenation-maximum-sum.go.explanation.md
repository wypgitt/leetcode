# 1191. K-Concatenation Maximum Sum - Go

## Go implementation notes
Kadane's algorithm is implemented over one or two virtual copies without materializing `arr * 2`.

## Go interview framing
In Go, explain both the algorithmic invariant and the concrete representation: slices for dense arrays/queues/stacks, maps for sparse lookup, structs for queue states or records, and channels or `sync` primitives for concurrency. Then walk through how the code mutates that representation while preserving the invariant.

## Core idea
The best subarray spans at most two boundary copies, plus full middle copies only when the total array sum is positive.

## Algorithm
1. Use Kadane's algorithm allowing an empty subarray, so the minimum answer is zero.
2. If `k == 1`, run Kadane on one copy.
3. Otherwise run Kadane on two copies to capture prefix-plus-suffix spans.
4. If total sum is positive, add `(k - 2) * total` for the middle full copies.

## Data structure choice
Only rolling Kadane variables are needed.

## Correctness argument
Any maximum subarray in repeated arrays either stays within one/two adjacent copies or, if it spans more, includes whole copies in the middle. Whole middle copies help only when the original total is positive, so the formula covers all optimal shapes.

## Complexity
Time is `O(n)` for one or two copies. Space is `O(n)` here due to `arr * 2`, which can be reduced to `O(1)` by iterating twice without materializing.

## Interview explanation
Start by naming the invariant: what state is being stored and why that state is sufficient. Then explain the transition or traversal in the same order the code executes. Finally, connect the stopping condition to the returned value. This keeps the explanation grounded in the code instead of sounding like a memorized trick.

## Tests and edge cases
- All-negative arrays return `0`.
- Positive total arrays benefit from middle copies.
- `k = 1` avoids adding nonexistent middle copies.

## Possible improvements
The current solution is chosen for clarity and interview reliability. If constraints were much larger, the main improvement would be to reduce the stated bottleneck in the complexity section, while keeping the same correctness invariant.
