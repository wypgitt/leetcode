# 1130. Minimum Cost Tree From Leaf Values - Go

## Go implementation notes
A monotonic stack is represented by `[]int`; push and pop are slice append and reslice operations.

## Go interview framing
In Go, explain both the algorithmic invariant and the concrete representation: slices for dense arrays/queues/stacks, maps for sparse lookup, structs for queue states or records, and channels or `sync` primitives for concurrency. Then walk through how the code mutates that representation while preserving the invariant.

## Core idea
Each leaf except the largest will eventually be multiplied by the smaller of its first greater neighbor on the left or right. A decreasing monotonic stack finds that partner greedily.

## Algorithm
1. Maintain a decreasing stack of leaf values with an infinity sentinel.
2. When a new value is greater than or equal to the stack top, pop the smaller middle value.
3. Pair that middle value with the cheaper of its two greater boundaries: `min(stack[-1], new_value)`.
4. After scanning, merge remaining stack values from smallest boundary upward.

## Data structure choice
A monotonic decreasing stack captures unresolved leaves waiting for a larger neighbor.

## Correctness argument
When `middle` is popped, both possible neighbors that can dominate it are known, and pairing it with the smaller one minimizes its unavoidable product contribution. This local greedy choice is independent of future larger values, so repeating it yields the global minimum.

## Complexity
Each value is pushed and popped once. Time is `O(n)`, space is `O(n)`.

## Interview explanation
Start by naming the invariant: what state is being stored and why that state is sufficient. Then explain the transition or traversal in the same order the code executes. Finally, connect the stopping condition to the returned value. This keeps the explanation grounded in the code instead of sounding like a memorized trick.

## Tests and edge cases
- `[6,2,4]` returns `32`.
- Increasing arrays repeatedly pop previous values.
- Decreasing arrays are resolved in the final cleanup.

## Possible improvements
The current solution is chosen for clarity and interview reliability. If constraints were much larger, the main improvement would be to reduce the stated bottleneck in the complexity section, while keeping the same correctness invariant.
