# 1138. Alphabet Board Path - Java

## Java implementation notes
`StringBuilder` is the right Java structure for repeated path-character appends.

## Java interview framing
In Java, call out the concrete collection or primitive array that carries the invariant. Arrays are best for dense indexed state, `HashMap`/`HashSet` for sparse lookup, `ArrayDeque` for queues and stacks, `PriorityQueue` for greedy minimum extraction, and `Semaphore`/monitor methods for concurrency. Then explain how each loop or recursive call updates that structure while preserving correctness.

## Core idea
Move from the current character's board coordinate to the target coordinate, taking special care around `z`, the only cell in its row.

## Algorithm
1. Convert each character to `(row, col)` with `divmod(index, 5)`.
2. Move up before moving right or down, so leaving `z` is safe.
3. Move left before moving down, so entering `z` is safe.
4. Append `!` after reaching each target letter.

## Data structure choice
A list of move characters is accumulated and joined at the end.

## Correctness argument
The movement order always stays within valid board cells. It reaches the exact target coordinate by changing row and column the required number of steps, and `!` records each target in order.

## Complexity
The number of moves is proportional to the produced path length. Space is also proportional to output length.

## Interview explanation
Start by naming the invariant: what state is being stored and why that state is sufficient. Then explain the transition or traversal in the same order the code executes. Finally, connect the stopping condition to the returned value. This keeps the explanation grounded in the code instead of sounding like a memorized trick.

## Tests and edge cases
- Targets containing `z`, such as `zdz`, validate invalid-cell avoidance.
- `leet` matches a normal board path.
- Repeated letters produce consecutive `!` with no movement.

## Possible improvements
The current solution is chosen for clarity and interview reliability. If constraints were much larger, the main improvement would be to reduce the stated bottleneck in the complexity section, while keeping the same correctness invariant.
