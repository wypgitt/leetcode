# 1146. Snapshot Array - Go

## Go implementation notes
Each index stores a sorted slice of `(snapID, value)` records. `sort.Search` performs binary search for historical reads.

## Go interview framing
In Go, explain both the algorithmic invariant and the concrete representation: slices for dense arrays/queues/stacks, maps for sparse lookup, structs for queue states or records, and channels or `sync` primitives for concurrency. Then walk through how the code mutates that representation while preserving the invariant.

## Core idea
Store only changes. Each index keeps a sorted history of `(snap_id, value)` pairs, and `get` binary-searches the latest value at or before the requested snapshot.

## Algorithm
1. Initialize every index history as `[(0, 0)]`.
2. `set` updates the current snapshot entry if one exists, otherwise appends a new pair.
3. `snap` returns the current id and increments it.
4. `get` uses binary search to find the rightmost record with `snap_id <= requested`.

## Data structure choice
Per-index sorted arrays are compact and make historical lookup logarithmic.

## Correctness argument
Every value change is recorded with the snapshot id in which it becomes visible. Binary search selects the most recent change not after the requested snapshot, which is exactly the value at that time.

## Complexity
`set` and `snap` are `O(1)`. `get` is `O(log k)` for changes at that index. Space is `O(number of sets + length)`.

## Interview explanation
Start by naming the invariant: what state is being stored and why that state is sufficient. Then explain the transition or traversal in the same order the code executes. Finally, connect the stopping condition to the returned value. This keeps the explanation grounded in the code instead of sounding like a memorized trick.

## Tests and edge cases
- Unset indices return `0`.
- Multiple sets before a snap keep only the latest value for that snap.
- Old snapshots remain unchanged after later sets.

## Possible improvements
The current solution is chosen for clarity and interview reliability. If constraints were much larger, the main improvement would be to reduce the stated bottleneck in the complexity section, while keeping the same correctness invariant.
