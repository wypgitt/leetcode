# 1143. Longest Common Subsequence - Go

## Go implementation notes
The DP is compressed into one `[]int` row, using a `previousDiagonal` variable to preserve the classic 2D recurrence.

## Go interview framing
In Go, explain both the algorithmic invariant and the concrete representation: slices for dense arrays/queues/stacks, maps for sparse lookup, structs for queue states or records, and channels or `sync` primitives for concurrency. Then walk through how the code mutates that representation while preserving the invariant.

## Core idea
Classic dynamic programming: `dp[j]` stores the LCS length between the processed prefix of one string and the first `j` characters of the other.

## Algorithm
1. Use the shorter string as the DP dimension to save memory.
2. For each character of `text1`, scan `text2` left to right.
3. Keep `previous_diagonal`, the old value of `dp[j-1]`, for the match transition.
4. If characters match, use diagonal plus one; otherwise keep the best of left and up.

## Data structure choice
A one-dimensional DP array represents the previous and current rows of the standard LCS table.

## Correctness argument
The recurrence considers the two exhaustive cases: matching current characters extend a smaller LCS, while nonmatching characters require skipping one current character. The 1D implementation preserves the same dependencies as the 2D table.

## Complexity
Time is `O(mn)`. Space is `O(min(m,n))`.

## Interview explanation
Start by naming the invariant: what state is being stored and why that state is sufficient. Then explain the transition or traversal in the same order the code executes. Finally, connect the stopping condition to the returned value. This keeps the explanation grounded in the code instead of sounding like a memorized trick.

## Tests and edge cases
- `abcde` and `ace` return `3`.
- No shared characters return `0`.
- Identical strings return their full length.

## Possible improvements
The current solution is chosen for clarity and interview reliability. If constraints were much larger, the main improvement would be to reduce the stated bottleneck in the complexity section, while keeping the same correctness invariant.
