# 1129. Shortest Path With Alternating Colors - Go

## Go implementation notes
The graph is a `[][][]int`: color, node, then neighbors. BFS states are small structs held in a slice-backed queue with a head index.

## Go interview framing
In Go, explain both the algorithmic invariant and the concrete representation: slices for dense arrays/queues/stacks, maps for sparse lookup, structs for queue states or records, and channels or `sync` primitives for concurrency. Then walk through how the code mutates that representation while preserving the invariant.

## Core idea
Shortest paths in an unweighted graph call for BFS, but the state must include the color of the last edge used.

## Algorithm
1. Build separate adjacency lists for red and blue edges.
2. Start BFS from node `0` with both possible last colors, so the first edge can be either color.
3. From a state `(node, last_color)`, only traverse edges of `1 - last_color`.
4. Record the first distance at which each node is reached.

## Data structure choice
A queue performs BFS. A `visited[node][color]` table prevents revisiting the same node with the same last-edge color.

## Correctness argument
BFS explores states in increasing path length. Since state includes last color, every generated path alternates by construction. The first time a node is assigned an answer is therefore the shortest alternating path to that node.

## Complexity
Each colored state and edge is processed at most once: `O(n + r + b)` time and space.

## Interview explanation
Start by naming the invariant: what state is being stored and why that state is sufficient. Then explain the transition or traversal in the same order the code executes. Finally, connect the stopping condition to the returned value. This keeps the explanation grounded in the code instead of sounding like a memorized trick.

## Tests and edge cases
- Graph with only red edges reaches one red step but cannot take two red steps.
- Parallel edges are harmless because visited filters states.
- Node `0` always has distance `0`.

## Possible improvements
The current solution is chosen for clarity and interview reliability. If constraints were much larger, the main improvement would be to reduce the stated bottleneck in the complexity section, while keeping the same correctness invariant.
