# 1169. Invalid Transactions - Go

## Go implementation notes
The parser uses `strings.Split` and `strconv.Atoi`, then groups indices by name in a map to limit pair comparisons.

## Go interview framing
In Go, explain both the algorithmic invariant and the concrete representation: slices for dense arrays/queues/stacks, maps for sparse lookup, structs for queue states or records, and channels or `sync` primitives for concurrency. Then walk through how the code mutates that representation while preserving the invariant.

## Core idea
A transaction is invalid if its amount exceeds 1000 or if another same-name transaction occurs within 60 minutes in a different city.

## Algorithm
1. Parse each transaction into name, time, amount, and city.
2. Immediately mark amounts over 1000 invalid.
3. Group transaction indices by name.
4. Within each name group, compare pairs and mark both invalid when time and city rules match.
5. Return original strings whose indices were marked.

## Data structure choice
A name-to-indices dictionary limits pair comparisons to relevant transactions.

## Correctness argument
The amount rule is checked directly. The city/time rule only applies to same-name pairs, and every such pair is examined, so every invalid transaction is marked and no unrelated transaction is marked.

## Complexity
Worst-case pair checking is `O(n^2)`, acceptable for the constraints. Space is `O(n)`.

## Interview explanation
Start by naming the invariant: what state is being stored and why that state is sufficient. Then explain the transition or traversal in the same order the code executes. Finally, connect the stopping condition to the returned value. This keeps the explanation grounded in the code instead of sounding like a memorized trick.

## Tests and edge cases
- Amount exactly `1000` is valid by amount rule.
- Transactions exactly 60 minutes apart are invalid if cities differ.
- Duplicate original strings are returned for each invalid occurrence.

## Possible improvements
The current solution is chosen for clarity and interview reliability. If constraints were much larger, the main improvement would be to reduce the stated bottleneck in the complexity section, while keeping the same correctness invariant.
