> **Focus areas:** Feed APIs · Ranking · Candidate generation · Video metadata · Thumbnails · Views · Personalization  
> **Style:** End-to-end product design with progressive scale (10× → 100× → 1,000×)  
> **Quality bar:** Correct arithmetic, explicit invariants, resolved ownership, honest MVP vs extreme-scale paths  
> **Interview theme:** Uber — **video home feed APIs and ranking/serving at progressive scale**

## 1. Clarify Requirements (Interview Q&A)

Goal: design YouTube-like home/subscription feed APIs including candidate generation, ranking/serving, metadata/thumbnail delivery, and view event logging—without building the entire video transcode farm in depth.

### 1.0 What this is / is not

| Dimension | This doc | Not this |
|-----------|----------|----------|
| Job | Feed generation + serve | Full CDN video byte distribution deep dive |
| Truth | Video catalog + graph + rank logs | Raw GOP encoding internals |
| Uber lens | Ranking + fan-out patterns akin to content feeds | Ignore latency budgets |
| MVP depth | Home feed + upload metadata hook | Live studio + ads auction full |

### 1.1 Functional Requirements

| # | Question to ask | Expected / typical interviewer answer | Design implication |
|---|-----------------|----------------------------------------|--------------------|
| F1 | Home feed? | Personalized ranked list | Rank service |
| F2 | Subs feed? | Following channels chronologic+rank | Fan-out/fan-in |
| F3 | Upload? | Metadata + process hook | Video service |
| F4 | Thumbnails? | CDN | Media |
| F5 | Views? | Count events | Ingest + approx counters |
| F6 | Continue watching? | Position | Watch state |
| F7 | Experiments? | A/B rankers | Expo |
| F8 | Safety? | Filter demotions | Policy |
| F9 | Latency? | Fast first page | budgets |
| F10 | Pagination? | Opaque tokens | cursors |
| F11 | Offline? | Limited | client cache |
| F12 | Search? | Sibling | Not core feed |

**MVP functional scope (lock with interviewer):**

1. Video metadata service (id, channel, title, duration, thumbs).
2. Candidate generators: subscriptions, trending, topic, co-watch.
3. Ranker blends candidates with lightweight features; business filters.
4. Feed API returns first page < budget; pagination cursors.
5. View/impression events to log pipeline; approximate view counts.
6. CDN URLs for thumbs; signed playback URLs (sketch).

**Out of MVP (explicitly defer):**

- Full ads auction
- Live multi-interactive
- Creator analytics suite complete

### 1.2 Non-Functional Requirements

| # | Question | Expected answer | Target |
|---|----------|-----------------|--------|
| N1 | Feed p99 | Home open | <200–300ms |
| N2 | Fresh upload | Appear to subs | seconds–minutes |
| N3 | Availability | Degrade to trending | fallback |
| N4 | Scale | QPS | See table |
| N5 | Privacy | Watch history | controls |
| N6 | Safety | Policy filters | pre-rank |
| N7 | Consistency | Views EC | approx OK |
| N8 | Cost | Candidate fanout | budgeted |

### 1.3 Cases (Flows & Edge Cases)

**Happy paths**

1. User opens app → feed API → ranked videos with thumbs.
2. New sub upload appears in subs candidates.
3. View event increments counters approx.
4. Pagination returns next distinct items.
5. Ranker experiment assigns stable stickiness.

**Edge / failure cases**

| Case | Behavior |
|------|----------|
| Celebrity channel upload fan-out | fan-in on read or limited fan-out |
| Cold start user | trending + survey topics |
| Deleted video in cursor | skip tombstones |
| Clickbait demotion | downstream signals |
| Ranker timeout | fallback heuristic |
| Thundering herd thumb | CDN |
| History off | no personalize |
| Duplicate candidates | dedupe by video_id |

### 1.4 Scales (Progressive)

| Metric | Baseline | 10× | 100× | 1,000× |
|--------|----------|----------|----------|----------|
| DAU | 50M | 500M | 2B | 2B+ |
| Feed QPS peak | 50K | 500K | 5M | edge |
| Videos | 100M | 1B | 10B | multi |
| Events/s views | 200K | 2M | 20M | sample |
| Channels hot | 1K | 10K | 100K | special |

**What each jump forces:**

- **10×:** Cache feed fragments; multi candidate gens
- **100×:** Feature store; tiered rank; fan-in subs
- **1,000×:** Edge; hierarchical trending; strict cost budgets

### 1.5 Etc. (Constraints & Assumptions)

- Design for retries, idempotency, and city/region isolation.
- Fail closed on authz/money; degrade intentionally on non-critical paths.
- Peak ≠ average; stadium/airport spikes are first-class.
- Transcoding/CDN playback exist as dependencies.
- Approximate counters fine for views.

**Scope statement:**

> Video home/subs feed: candidates, ranking, feed API, metadata/thumbs, view logs—progressive scale with fallbacks.

## 3. High-Level Design

### 3.1 Core abstractions

```text
Video
Channel
CandidateSet
RankedFeedPage
WatchState
Impression/ViewEvent
```

### 3.2 Options & trade-offs

| Option | Pros | Cons | Deal-breaker when |
|--------|------|------|-------------------|
| A. Pure chronological global | Simple | Poor relevance | Home |
| B. Write fan-out feed per user | Fast read | Celebrity explode | Hot channels |
| C. Hybrid fan-in + ranked candidates + cache | Balanced | More systems | — chosen |
| D. Single monster ML model sync | Quality? | Latency/fail | No fallback |

**Chosen path:**

- Hybrid: lightweight candidate gens → L1/L2 rank → cache per user fragment short TTL.
- Subs: fan-in pull recent from followed channels inverted index.
- Fallback trending when personalize fails.

### 3.3 Core design mechanics

**Feed request:** auth → experiment → candidates (parallel) → filter safety/dedupe → rank → paginate → log impressions.

**Invariant:** pagination stable enough to avoid dupes within session; deleted videos skipped; privacy flags honored.

### 3.4 API sketch

```text
GET /v1/feed/home?cursor&limit
GET /v1/feed/subscriptions?cursor
GET /v1/videos/{id}
POST /v1/videos (metadata after upload)
POST /v1/events/views {video_id, position, ts, client}
GET /v1/playback/{id}/manifest  # sketch dependency
```

### 3.5 Trade-offs summary

| Decision | Trade-off |
|----------|-----------|
| Fan-out vs fan-in | Read latency vs write amplification |
| Deep rank | Quality vs p99 |
| Short cache TTL | Fresh vs load |
| Approx views | Cost vs exact |

## 5. Design Deep Dive

### 5.1 Reliability

- Ranker timeouts → fallback.
- Cache stale-ok.
- Event pipeline at-least-once.
- Tombstones for deletes.

**Delivery / consistency cheat-sheet**

| Layer | Guarantee |
|-------|-----------|
| Client → API | At-least-once; idempotency keys where mutations exist |
| System of record | Single-writer per entity / partition key |
| Downstream effects | At-least-once via outbox/stream; idempotent consumers |
| Reads | Read-your-writes on primary; replicas may lag |

**Deal-breakers**

- No fallback when ML down
- Unbounded celebrity write fan-out
- Feed duplicates every scroll from bad cursors

### 5.2 Scalability

- Shard users for cache; shard videos; hierarchical trending; sample events; edge feed for anonymous.

**Progressive evolution**

| Scale | Architecture posture |
|-------|----------------------|
| Baseline | Single region/city; simple durable store + stream |
| 10× | Shard by city/entity; split hot paths |
| 100× | Cells, async fan-out, careful caching, hot-key splits |
| 1,000× | Hierarchical aggregation, edge where safe, strict cost/isolation |

### 5.3 Maintainability

- Ranking offline eval; feature coverage monitors; experiment clean-up.

- Versioned schemas/configs with rollback.
- Golden fixtures and replay tools for disputes/regressions.
- Published ownership boundaries between services.
- SLOs tied to user-visible failures; load-test stadium/airport peaks.

### 5.4 Multi-region clarity

| Plane | Mode |
|-------|------|
| Edge / API gateways | Active-active |
| Mutable entity writes | Home cell / city region single-writer |
| Caches / projections | Regional, eventually consistent |
| Analytics | Async lake / warehouse |

### 5.5 Security, privacy, abuse

- Signed playback; auth on history; abuse scrape rate limits; child/safety policies.

## 6. Wrap-Up

**What to say in 60 seconds**

> YouTube-like feed serving is a hybrid candidate→rank→cache pipeline with subscription fan-in, safety filters, approximate view analytics, and hard latency fallbacks—not a single magical model call.

**MVP → next**

1. MVP: invariants + audit/outbox + single-city correctness.
2. Next: sharding, richer consumers, degradation playbooks.
3. Later: edge optimizations, hierarchical aggregation, advanced models with caps.

**Top risks**

| Risk | Mitigation |
|------|------------|
| Hot keys / stadiums | Split shards, jitter, admission control |
| Retry storms | Idempotency, client jitter, coalescing |
| Inconsistent side effects | Outbox + consumer idempotency |
| Cost explosion | Sampling, TTL, tiered storage |
| Trust / correctness bugs | Audit, clamps, kill switches |

## 7. Deeper / Related Interview Questions

### Fan-out

**Q: Celebrity 100M subs?**  
A: Don’t write 100M feed rows; fan-in pull + rank.

### Latency

**Q: Ranker slow?**  
A: Cached features, L1 light model, deadline + fallback.

### Scale & multi-region

**Q: How do you shard?**  
A: City/region cell first, then hash entity id within the cell.

**Q: Active-active writes for the same entity?**  
A: Avoid; home-cell single-writer with fencing on failover.

**Q: What do you shed first under load?**  
A: Non-critical analytics/marketing; protect money, safety, and trip-critical paths.

### Interview arithmetic / trap questions

**Q: When do units go wrong?**  
A: Mixing MB/GB/PB; using average instead of peak; forgetting retries amplify QPS; storing forever without sampling.

**Q: What do you defer explicitly?**  
A: Active-active multi-writer; perfect exactly-once for arbitrary side effects; unbounded history in primary OLTP.

**Q: What is the system of record?**  
A: Name it aloud—everything else is a projection/cache.

### Additional operational notes

- Page on SLO burn, not on every transient blip; use multi-window burn rates.
- Separate **user-facing errors** from **dependency noise** in dashboards.
- Keep a per-city feature flag for emergency degradations.
- Document ownership: on-call, codeowners, escalation path.
- Every external callback needs authentication and replay protection.
- Prefer additive schema changes; use explicit version fields on events.
- Load tests should include retry amplification (clients with 3× retries).
- Stadium and airport topologies are mandatory soak scenarios.
- Archive policy must be tested via restore drills, not only backups.
- When in doubt in interview: state invariant, then mechanism, then trade-off.

### Capacity planning worksheet (fill in interview)

```text
peak_qps = avg_qps × peak_factor (often 3–10×)
headroom = 1.5–2× peak for shard imbalance
storage_hot = entities_active × bytes × retention_hot
storage_cold = events_day × bytes × retention_cold × sample_rate
network = qps × payload × fanout
timers_or_connections = concurrent_sessions × cost_each
```

4. Separate **control plane** (config, experiments) from **data plane**.
5. For money: minor units, idempotency, audit, reconciliation.
6. For realtime: define freshness with a number.
7. For 1000×: talk cells, hierarchical aggregation, cost budgets.
8. End with risks + kill switches.

### Additional operational notes

- Page on SLO burn, not on every transient blip; use multi-window burn rates.
- Separate **user-facing errors** from **dependency noise** in dashboards.
- Keep a per-city feature flag for emergency degradations.
- Document ownership: on-call, codeowners, escalation path.
- Every external callback needs authentication and replay protection.
- Prefer additive schema changes; use explicit version fields on events.
- Load tests should include retry amplification (clients with 3× retries).
- Stadium and airport topologies are mandatory soak scenarios.
- Archive policy must be tested via restore drills, not only backups.
- When in doubt in interview: state invariant, then mechanism, then trade-off.
